# 首轮独立措辞挑战与真实试用准备

## 结论

工程回归覆盖的路径已经可运行，但当前有限规则解析对自然措辞明显脆弱，不能用原有固定回归全部通过来推断真实用户也能顺利使用。本轮没有修改业务解析器，保留首次暴露问题的成绩作为改进基线。

## 方法与可复现边界

- 待测应用版本：`5f3e41aa6a4188527fdc59d25e52ae5e4cdc4d31`。
- 独立测试代理只看业务指南和V3种子事实，未看解析代码、旧测试、旧评测或结果；编写24个场景33次请求，运行前冻结文件SHA256。
- 用例由agent生成，非人类留出集，也不是真实用户试用。公开指南含示例，不能宣称完全隔离产品文档或统计独立。
- 每个场景创建新会话，按预期标签核对条件；多轮任务只有全部回合通过才计成功。标签中的商品名称严格保留完整指称，商品卡片另按实际标题和金额核对。
- 模糊/不支持要求应澄清。即使输出费用公式正确，漏掉预算、时效或未支持要求后照常返回商品也不能通过。
- 测试集冻结及设计说明：[LANGUAGE-CHALLENGE.md](../agent-service/evaluation/LANGUAGE-CHALLENGE.md)。完整输入、标签和实际输出：[原始报告](validation/language-challenge-20261022.json)。

## 实测结果

| 指标 | 本轮结果 |
| --- | --- |
| 整段任务严格通过 | 3/24，12.5% |
| 请求严格通过 | 4/33，12.1% |
| 返回商品对外部标签的约束满足率 | 21/42，50.0% |
| 应澄清请求正确处理 | 2/6 |
| 串行请求耗时 | p50 14.10ms，p95 20.59ms |
| 服务端模型调用/模型费用 | 0次 / 0美元；不含编写评测的模型、人力及基础设施费用 |

分组按请求：预算0/4、时间1/3、具体商品1/3、数量0/3、独立澄清场景1/5、多轮1/15。多轮中的另一澄清回合计入多轮分组，所以澄清请求总数是6。

分数包含两类问题，不能混为一谈：例如“燕麦拿铁”解析为“拿铁”，本次返回的商品虽然恰好正确，严格条件记录仍不合格；而预算漏掉后返回超预算商品则是实际错误。报告保存了两层结果，便于逐项复核。该挑战集刻意覆盖语言变化，样本小、非随机，不能据此估计真实用户总体成功率。

## 具体失败与改进顺序

| 用户表达 | 实际行为 | 问题 |
| --- | --- | --- |
| 东区咖啡，“手里只有十六块九，所有费用都从这里出” | 预算为空，返回17元拿铁 | 实际超预算 |
| 北区咖啡，“给你一刻钟送到” | 时限为空，返回18/25分钟商品 | 实际超过时限 |
| “最多二十元” | 部分请求未记录预算，返回23元方案 | 金额口语未识别 |
| “不赶时间了，多久送都可以” | 保留旧18分钟限制 | 多轮清除意图未识别 |
| “必须零乳糖” | 返回拿铁，未说明缺少成分依据 | 不支持要求被忽略 |
| “燕麦拿铁”“经典美式”等完整名称 | 仅保存“拿铁”“美式”等款式词 | 丢失细分商品要求，当前样本可能碰巧正确 |

下一轮应先建立“识别到要求却无法确定时必须澄清”的机制，并用明确结构化表单作为可控入口；再比较规则与模型抽取方案，继续让价格计算和硬约束校验保持确定性。仅按这24个案例补关键词会改善回归，但不足以证明泛化。

本轮数据已经被查看，后续修复后应将其视为开发回归集，并用新的独立措辞或真实参与者表达做下一轮验证。任何重新标注都应留下版本和原因，不能悄悄删掉失败。
