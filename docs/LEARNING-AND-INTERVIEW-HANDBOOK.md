# reco-onx：从第一次运行到独立讲清设计

> 阅读对象：能写基础 Java/Python，但还不能把项目完整讲清的人。先操作，再跟踪一次请求，最后回答设计取舍。文档描述当前代码，不把演示能力包装成生产经历。

## 1. 用一分钟说明项目

这是一个使用合成校园商家数据的本地生活推荐决策服务。用户提出区域、预算、商品和配送时限，服务依次调用商家、商品、配送报价工具，计算完整到手价，严格过滤硬约束，返回匹配方案；没有合适结果时解释原因并请求用户确认放宽。多轮对话保存结构化约束，明确要求才记录长期偏好。请求标识与数据库事务支持重试和已提交结果恢复。

当前主流程是 **FastAPI + LangGraph + 有限中文规则 + MySQL**。本地生活路径不调用大模型，不应说成“已经验证复杂开放式语言理解”。可选 LLM 接口属于历史推荐／问答路径。Java 推荐 DAG 仍保留，用于介绍并行召回、超时和推荐工程；面试主线建议聚焦本地生活，避免把两条路径混在一起。

## 3. 第一次运行

安装 Docker Desktop（或 Docker Engine + Compose）、JDK 17、Maven 3.9+。仓库根执行：

```sh
mvn -DskipTests package
docker compose up --build -d
docker compose ps
```

打开 `http://localhost:18081/`，选择演示用户和“本地生活（演示）”。Java 服务在宿主机 `18082`，MySQL 在 `3307`，Python Agent 在 `18081`。容器之间使用服务名及容器端口，不使用宿主机映射端口。Redis 默认只在 Compose 网络内开放。

依次输入：

1. `北区咖啡预算20元，30分钟内送达`。
2. `一刻钟送到`：如果没有满足时限的方案，应解释无匹配，不得返回更慢方案。
3. `多久送都可以`：清除旧时限。
4. `只有十六块九`：预算为 1690 分，17 元商品不能作为匹配结果。
5. `燕麦拿铁预算30元`：保留完整名称；同类替代显示在单独区域，需要确认。
6. `必须零乳糖`，再 `继续查询`：数据没有成分证明，持续澄清，不能因为下一轮没重复要求就推荐。
7. `取消零乳糖要求`：只解除对应要求。若同时声明了坚果过敏，仍然不能推荐。

必要时新建会话做独立实验，避免上一轮约束影响结果。界面的“体验用户”是模拟身份，不是已经完成的生产登录系统。

启动失败先看：

```sh
docker compose logs --tail=100 db app agent redis
curl http://localhost:18081/health
curl http://localhost:18082/health
```

MySQL 健康只代表数据库可连接；还要确认 Java 启动执行 Flyway V1–V4 成功。旧库需要增量迁移，不要修改已应用 SQL 来强行通过 checksum。保留用户数据时不要执行 `docker compose down -v`。

## 5. 跟踪一次请求

```text
用户消息 + user/session/request 标识
  → 校验输入及演示用户
  → 开启 READ COMMITTED 事务，锁定该用户会话
  → 查同一请求是否已完成，检查 payload 指纹
  → 读取有效会话快照与长期偏好
  → 解析本轮输入、合并条件、更新未解决饮食要求
  → 需要澄清？返回无推荐的澄清结果
  → search_merchants → search_products → quote_delivery → decide
  → 原子保存任务、会话状态、对话审计与明确记忆
  → 提交事务，返回报价、工具轨迹、约束来源
```

这是一条受约束工作流，不是让模型任意选择工具。LangGraph 明确了节点边界和状态传递；可靠性还依赖普通 Python 校验和数据库事务。`toolTrace` 便于定位“商家没覆盖”“商品售罄”“配送报价失败”等不同原因。

同会话串行化可以避免两个并行追问互相覆盖，但也意味着慢工具会延长数据库锁持有时间。目前工具是本地 SQL，事务范围可控；接入远程工具时应拆分取数、版本校验和提交，不应把几十秒外部请求放在数据库锁内。

## 6. 约束建模与多轮合并

`LocalConstraints` 的核心字段：

| 字段 | 语义 |
| --- | --- |
| `zone` | north / south / east，非真实经纬度 |
| `category` | coffee / meal / grocery |
| `product_query` | 完整商品名称／标题匹配词 |
| `product_match_mode` | prefer 可给单独替代项；exact 不替换 |
| `max_total_cents` | 整笔到手预算，单位分，可为空 |
| `max_delivery_minutes` | 从现在起预计送达上限，可为空 |
| `quantity` | 同一 SKU 的份数，1～10 |

优先级：**长期偏好 < 当前会话 < 本轮文本 < 本轮结构化参数**。省略字段表示沿用；显式 `null` 才是清除预算／时间限制。不要把“未提及”和“不限制”合并成一种状态。

例子：上轮是北区、20 元、20 分钟；本轮“多久送都可以”只把时间改为空，预算和区域不变。“咖啡改成两杯”不应清空燕麦拿铁；明确换成简餐时，应清除原咖啡商品名，避免跨品类残留。

饮食要求另外存为 `pendingRequirements`。原因是现有商品数据无法证明过敏原、乳糖或糖分；强行把它映射为标题词会产生错误保证。这些要求不因普通追问消失，也会阻止旧结果重放。撤销采用明确范围：取消零乳糖不取消坚果过敏；“不要取消”不执行撤销；复合句无法可靠拆分时保留并要求明确说明。

中文数字也有歧义：“一百二”可能是 120，不能擅自解释成 102。本轮对这种缺单位表达要求澄清，明确的“一百零二”“一百二十”分别按 102、120 处理。规则仍有语言边界，未见表达需要新评测或结构化输入兜底。

## 7. 商品名称和替代方案

“燕麦拿铁”是完整商品意图，“拿铁”是用于寻找同类替代的家族词。不能在存储时只留下家族词，否则下一轮改预算会忘记用户要燕麦款。

`prefer` 模式先返回完整匹配，替代放在 `alternativeItems`，标记 `requiresConfirmation`。`exact` 模式只返回完整匹配。同类替代也必须满足预算和时间。是否更便宜不能覆盖明确的商品要求。

现有自然语言词表有限，不代表所有新口味和品牌都能正确识别。对未建模名称优先使用结构化 `product_query`；未来应把商品词典与目录同步，并在提交推荐前展示识别到的完整条件供用户确认。商品标题包含“燕麦”不等于已获得零乳糖检测证据。

## 8. 到手价、排序与有效期

所有钱都用整数分：

```text
商品小计 = 单价 × 数量
包装 = 单件包装 × 数量
配送 = 满免配门槛 ? 0 : 配送费
优惠 = 满优惠门槛 ? min(优惠金额, 商品小计) : 0
到手价 = 商品小计 + 包装 + 配送 - 优惠
```

当前门槛按优惠前商品小计判断，不包含包装和配送。别默认所有平台都这样；接真实平台时由供应商报价协议确定。

依次剔除不可售、库存不足、价格无效、起送不足、区域不覆盖、规则过期、超预算和超时方案，再排序。排序关键字为到手价、预计时效、商品 ID，确定性相同输入得到可复现结果。完整匹配和替代分区展示。

报价最长 120 秒有效，不能超过底层规则有效期。数据库恢复的旧任务也会重新判断过期，而不是无条件展示“成功”。报价不预占库存，也不执行下单／支付，不能承诺实际履约。

## 9. 数据与事务

商家、商品、配送规则是三个独立工具边界，共用 MySQL；它们不是三个独立部署的微服务。种子数据标记 `synthetic-campus-v1`，没有实际商家授权或真实交易。

会话快照保存当前结构化约束及过期时间。任务记录保存请求指纹和结果。对话日志用于展示与审计，不以“最后几条聊天文本”作为唯一业务状态。长期偏好仅在明确记忆请求时写入，并有有效期。Redis 用于辅助短期状态，MySQL 是本地生活任务与约束的持久化依据。

为什么必须一个事务？若结果保存了但会话没保存，下一轮就会按旧条件执行；若记忆保存了但任务失败，用户看到失败却产生跨会话偏好。原子提交把这些状态关联起来。坏输入不会覆盖有效约束快照，但未解决饮食要求仍需单独持久化。

## 10. 幂等和恢复

| 情况 | 当前行为 | 不能承诺的内容 |
| --- | --- | --- |
| 同请求键、同内容重发 | 返回已保存任务，标记 replayed | 不等于报价仍有效 |
| 同键、不同内容 | 409 冲突 | 不能用重试键修改条件 |
| 提交前进程崩溃 | 事务回滚，可原键重试 | 不恢复每个图节点的执行栈 |
| 提交后响应丢失 | 重发读取已提交结果 | 不是“网络恰好一次投递” |
| 报价过期 | 要求重新查询 | 不锁库存与价格 |
| 有未解决饮食要求 | 旧任务读取也阻止推荐 | 不推断食物安全 |

当前只读工具重试较容易。如果以后增加下单：先定义外部幂等键、订单状态、超时后的查询接口、补偿和对账，不能仅重跑整个图。当前项目不具备支付级别的副作用恢复。

RUN_LOCAL_LIFE_DB_TESTS=true MYSQL_HOST=127.0.0.1 MYSQL_PORT=3307 python -m unittest discover -s tests -v

第一条默认跳过真实 MySQL 测试。第二条需要启动且迁移好的模拟数据库；如果没有 Redis 端口映射，按 Compose 网络方式运行测试或配置本地 Redis。不要把“skipped”算作通过。

RUN_TESTCONTAINERS=true mvn verify

固定集用于防回归。修过的语言挑战已经成为已知用例，不能继续称为新的独立留出集。模拟用户脚本也不能称为真实用户满意度调查。

## 12. 独立语言评测与真实试用

可以自行做自动化评测与模拟试用；无法自行生成“真实独立用户反馈”。操作方法：

1. 先写任务契约：预算单位、时限、完整商品、撤销范围、必须澄清的未知成分。
2. 在看解析代码之前收集全新措辞；每条附逐轮预期字段、状态和禁止推荐条件。可以用不同模型出题，但仍需人工校对预期。
3. 冻结 JSON 与版本哈希。开发集用于修复，留出集首次测试后记录原始失败，不覆盖历史报告。
4. 同时报告约束满足率、任务成功率、澄清是否必要、P50/P95 耗时、真实模型调用费用。当前本地路径不调用模型，模型费用为 0，但不代表服务没有成本。
5. 让 3～5 位未看实现的同学按 `docs/pilot` 任务试用；让他们自己组织语言，观察员不要教关键词。记录卡住点、修改轮数和最终是否符合预期，获得同意并避免采集无关个人信息。
6. 把问题变成回归测试，再找新措辞复测；不要把同一批人被教会后的成功率当作泛化提升。

使用模拟用户时覆盖身份隔离、同键并发、断连重发、跨会话偏好、未解决饮食条件；自动执行这些有价值，但与真实用户可用性是不同证据。

## 13. 常见排查

| 症状 | 先检查什么 |
| --- | --- |
| 时间不限后仍过滤 | patch 是否有显式 null；是否误用了旧请求键 |
| 只改数量却换了商品 | product_query 是否被清空；是否误判品类变化 |
| 17 元超过 16.9 元预算 | intent 是否 1690；比较的是 totalCents 还是标价 |
| 重启后条件丢失 | MySQL 会话写入是否提交、TTL、用户和 session 是否相同 |
| 旧账号结果出现在新页面 | 异步回调是否检查当前用户和会话 |
| 工具失败但页面像成功 | 状态是否 tool_error；是否错误展示缓存卡片 |
| CI 几秒失败 | 首个失败步骤／Annotations、Action 解析及权限；别先假定业务测试失败 |

此前 GitHub 通知中两个 Python 作业数秒失败、Java 作业成功，仅凭截图无法确定原因。固定 Action SHA 和本地检查已经做过，但未读取到远端日志前不能宣称根因已证实或远端已全绿。应在 Actions 中看失败步骤原文。

## 14. 面试问答练习

**为什么用 LangGraph？** 把商家、商品、配送和决策拆成显式状态图，工具轨迹和失败边界容易观察。它不自动提供业务正确性，预算与状态规则仍需类型校验、测试和事务。

**为什么不用纯 LLM 回答？** 价格和库存来自可验证工具，金额由确定性代码计算。当前本地路径甚至不调用 LLM；下一步可用模型抽取结构化约束，但必须验证字段、保存证据并跑独立评测。

**是不是智能体？** 可以称为受约束的工具工作流／Agent 工程演示，说明自治程度有限；不宣称任意任务规划。

**预算能稍微超一点吗？** 只有用户明确授权才能改约束；系统可建议，但不能偷偷放宽。预算比较完整到手价，不是商品标价。

**为什么用整数分？** 防止二进制浮点误差造成边界比较不稳定；优惠分摊等未来复杂规则还要定义舍入策略。

**怎么区分记忆和上下文？** 当前会话约束服务本轮连续任务；长期偏好跨会话，仅明确记住才保存；本轮修改优先于旧记忆。

**为什么未知成分不推荐？** 标题不是成分证据，失败成本较高。持久化未解决要求，直到明确撤销或结束任务。

**并发两轮会怎样？** 同会话数据库锁串行化，避免读旧快照后相互覆盖。多会话可并行，跨会话长期偏好的冲突还需明确产品规则。

** exactly-once 做到了吗？** 没有宣称网络恰好一次。唯一请求标识、内容指纹和事务保证该请求的业务结果不会重复提交，调用仍可能重试。

**Redis 挂了能运行吗？** 本地生活持久状态以 MySQL 为准；具体入口的缓存降级应按测试和日志确认，不能笼统说任何路径都不受影响。

**工具现在独立吗？** 接口职责独立、共库部署。拆成远程服务后需增加超时、熔断、限流、版本与一致性策略。

**评测通过率能说明什么？** 说明固定数据和断言下的回归表现；不能代表所有中文表达，也不能代替真实用户试用。

**如何优化延迟？** 先分解解析、SQL、工具、事务锁等待；缓存稳定目录，缩短锁内工作。不要盲目并行有数据依赖的节点。

**真实业务下一步是什么？** 优先身份鉴权、商品目录对齐、成分证据、供应商报价适配、独立语言集和用户试用；之后才是下单副作用。

## 15. 简历与仍需改进的目标

可写：“实现本地生活约束推荐工作流，支持完整到手价计算、多轮约束与显式长期偏好；用 MySQL 事务和请求指纹实现幂等重试与结果恢复，构建语言、业务、数据库和浏览器回归测试。”数量和耗时必须引用对应版本的真实报告，不填写估算的线上吞吐或用户量。

优先级建议：

1. **真实试用前**：展示解析后的完整约束，让用户能逐项修改；补充目录未见名称、撤销否定和数字歧义的独立用例。
2. **公开部署前**：生产登录与授权、接口限流、隐私和数据删除、密钥管理、数据库备份与监控；现有演示 ID 不能作为身份凭证。
3. **接真实供应商时**：保留数据来源和更新时间、验证报价协议、处理网络超时与供应商限流；不抓取未经授权接口。
4. **需要下单时**：外部幂等、订单持久状态、支付与库存补偿、对账。

学完的自测标准：不用背代码，能画请求图，解释一个正常流程、一个语言歧义、一个数据库竞争、一次响应丢失，以及为什么不能把燕麦拿铁当成零乳糖保证。对尚未实现的部分能讲清方案和验证办法，比声称“没有问题”更可靠。
