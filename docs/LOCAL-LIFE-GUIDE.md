# 本地生活 Agent：使用、实现与验证

> 2026-10-22 补充：指定商品名称、中文数字、UTC数据库连接、偏好重新生效及会话切换隔离已完善，详见 [本轮改进与验证](IMPROVEMENTS-20261022.md)。

## 当前完成程度

reco-onx 已新增可运行的本地生活决策流程：解析需求 → 查询覆盖商家 → 查询可售商品 → 计算配送报价 → 按硬约束过滤 → 按完整到手价排序。原有 goods/live/ad 推荐和项目问答保留，通过界面模式切换或 `workflow` 选择。

这是**使用自建合成数据的校园即时零售演示**。商家、商品和配送工具有独立接口，但共用 MySQL，并非三个独立部署的服务。无真实平台接入、下单、支付或库存预占。

| 原目标 | 当前实现 | 仍需深化 |
| --- | --- | --- |
| 预算、位置、品类、配送 | 区域、品类、商品名称、到手预算、送达分钟、单品数量 | 真实地址、复杂口语、跨品类组合 |
| 商家、商品、配送工具 | 三个独立逻辑工具和 LangGraph 节点轨迹 | 外部供应商适配、网络失败和限流 |
| 完整到手价 | 商品、包装、配送、优惠，整数分计算 | 跨店购物车、叠加优惠规则 |
| 无结果时解释并询问 | 返回失败原因计数、需要确认的调整建议；不自动放宽 | 收集真实用户对澄清体验的反馈 |
| 临时条件和长期偏好 | 结构化会话快照；明确要求才保存长期偏好 | 偏好管理界面、删除与过期策略 |
| 失败与恢复 | 原子回滚、同键重试、已提交结果重放、过期报价拒绝 | 外部有副作用工具的幂等与持久化任务恢复 |
| 效果评估 | 固定回归集、约束检查、耗时和模型成本字段 | 独立留出集、真实模型及用户评测 |

## 运行与演示

沿用根目录 README 的 Docker Compose 启动方式。Java 后端启动时由 Flyway 自动应用 V1–V3；已有数据库会增量应用 V3。不要修改已应用迁移或删除已有数据来升级。

浏览器打开 `http://localhost:18081/`，选择体验用户，默认进入“本地生活（演示）”。依次尝试：

1. `北区咖啡预算20元，30分钟内送达`：便利店美式到手14元，低于标价8元、到手17元的另一方案。
2. `20分钟内送达`：保留区域、品类、预算，筛掉25分钟方案，选择18分钟、17元方案。
3. `预算改为14元`：没有同时满足预算和时间的方案，解释冲突并建议调整；不会偷偷放宽。
4. `时间不限`：用户明确解除时间限制，重新得到14元方案。
5. `改成2杯`：保持其余条件，按数量重新计算包装、配送和优惠。
6. 新建会话后输入 `记住，以后在东区买咖啡`：只在明确记忆请求时保存长期偏好；`这次去北区` 不改长期偏好。

卡片展示费用拆分、预计送达时间和有效期。报价过期后显示重新查询提示。连接中断可点击“重试上次请求”，沿用本地保存的请求标识。刷新页面后聊天文字可恢复，历史报价卡片不自动重建；需要查询已提交任务时使用下文任务接口。

## 数据来源与计算规则

种子数据位于 [`V3__local_life_tools.sql`](../db/migration/V3__local_life_tools.sql)，来源标记 `synthetic-campus-v1`。所有名称、价格、库存和时效均为测试场景构造，没有抓取真实平台或暗示真实商家承诺。

支持北区 `north`、南区 `south`、东区 `east`，品类为咖啡 `coffee`、简餐 `meal`、便利食品 `grocery`。一次比较一种商品、数量1–10；不计算混合购物车。

```text
商品小计 = 单价 × 数量
包装费 = 单件包装费 × 数量
配送费 = 达到免配送门槛 ? 0 : 区域配送费
优惠额 = 达到优惠门槛 ? min(设定优惠额, 商品小计) : 0
到手价 = 商品小计 + 包装费 + 配送费 - 优惠额
```

门槛均比较优惠前商品小计；不计包装及配送。所有金额使用人民币整数分，避免浮点误差。商品售罄、商家停业、配送不覆盖、未达到起送门槛、报价规则过期、价格缺失或非法时不产生可购买方案。

预算和时间都是硬约束，等于边界允许。先过滤，再按到手价、预计分钟、商品ID排序，最多返回3项。报价有效期最多120秒，若配送规则先过期则取更早时间；报价不锁定库存，也不是履约承诺。

## API 与语言边界

```bash
curl -s http://localhost:18081/api/local-life/recommend \
  -H 'Content-Type: application/json' \
  -d '{"user_id":789,"session_id":"local-demo","request_id":"demo-request-001","message":"北区咖啡预算20元，30分钟内送达"}'
```

`/api/chat` 也支持 `workflow: "local_life"`。显式 `workflow: "recommendation"` 使用原有推荐/问答分支；`auto` 根据本轮信号和有效会话路由。产品调用建议显式传模式，避免意图歧义。

结构化调用可以绕开有限的自然语言规则：

```json
{
  "user_id": 789,
  "session_id": "local-structured",
  "request_id": "structured-001",
  "message": "查询这些条件",
  "constraints": {
    "zone": "north",
    "category": "coffee",
    "product_query": "拿铁",
    "max_total_cents": 2000,
    "max_delivery_minutes": 30,
    "quantity": 1
  }
}
```

`product_query` 是商品标题的字面包含条件，不能推断过敏原或配料；没有匹配商品时不自动换款。文本识别美式、拿铁、冷萃等已建模词。只改预算/数量会保留商品限制；明确重选品类（如“咖啡”“简餐”）、“不限款式”或“取消商品限制”会清除旧商品限制。结构化设置 `category` 而未指定 `product_query` 时也会清除旧限制。

其余字段省略表示保留已有条件；预算或时间显式 `null` 表示清除限制。`constraints` 只允许声明的字段及合法类型/范围。优先级：长期偏好 < 当前会话快照 < 本轮文本 < 本轮结构化字段。

当前本地生活路径采用有限中文规则解析，不调用模型。支持示例中的阿拉伯数字，以及带元/分钟/杯等单位的0～99中文整数、分钟/半小时、数量、区域和品类修改，以及取消预算/时间限制；不是通用自然语言理解器。已识别的未知区域、糖度/过敏等不支持条件会要求澄清，但无法保证识别所有未见表达。对复杂输入使用结构化参数，后续扩展必须增加独立评测，不能只添加关键词并宣称理解能力提升。

结果状态包括 `completed`、`clarification`、`no_match`、`tool_error`、`quote_expired`。无匹配建议中的 `requiresConfirmation` 表示需要用户决定，系统不会自行应用。返回 `taskId` 后，可携带体验登录令牌访问 `GET /api/local-life/tasks/{taskId}?token=...`；只能读取当前体验用户的任务。HTTP 推荐入口仍允许直接传演示用户ID，整体身份体系仅供本地演示，不是生产鉴权。

## 状态、幂等与恢复设计

核心文件：

- [`local_life.py`](../agent-service/app/local_life.py)：输入约束、有限文本解析、报价和图决策。
- [`local_life_store.py`](../agent-service/app/local_life_store.py)：三个SQL工具、会话快照、事务、幂等任务和偏好写入。
- [`main.py`](../agent-service/app/main.py)：路由、HTTP/WebSocket、演示会话与旧工作流。

每次本地生活请求开启 MySQL `READ COMMITTED` 事务，并锁定 `(user_id, session_id)` 会话行。会话条件、任务结果、两条对话审计和明确的长期偏好更新一起提交。同会话请求串行，不同会话可并行。此事务只执行本地数据库读取和规则计算；未来远程工具不能照搬长事务设计。

`(user_id, session_id, request_id)` 唯一约束配合请求内容摘要：

| 情况 | 行为 |
| --- | --- |
| 新请求 | 执行并原子提交 |
| 同键同内容重复或并发 | 返回同一个任务，审计不重复 |
| 同键改内容 | HTTP 409，调用方应给新需求分配新键 |
| 提交前异常/进程退出 | 事务回滚；同键重新执行 |
| 提交后响应丢失/进程重启 | 从MySQL重放已提交结果 |
| 重放时任一报价已过期 | 返回 `quote_expired`，不返回旧报价卡片；新键重新报价 |

客户端必须在发送前保存请求键，恢复时复用键；未传键的请求不能依靠重发获得同样的幂等保证。已完成任务重放与会话恢复不等于 LangGraph 节点断点续跑，目前没有后台自动恢复执行器。

会话快照默认有效期24小时（可通过 `AGENT_SHORT_MEMORY_TTL_SECONDS` 配置），独立于最近8条聊天窗口，因此连续多轮也不会丢失仍有效的条件。长期偏好沿用现有表，使用 `local.*` 命名空间。仅“记住／以后／长期偏好”且没有临时语义才写入；明确清除某个长期约束会删除相应键。解析存在不支持条件时不污染快照或偏好。

查询单品候选在商品名称过滤前超过200条时明确结束为工具错误，避免把截断召回错误地解释为“全库无结果”。当前只适合小规模演示数据；后续应实现可证明完整性的分页或数据库约束下推。

## 验证与结果解释

运行方式见 [测试说明](testing.md)。2026-10-21 在当前云环境的结果：

- Python 50项全部通过，其中8项使用真实MySQL；覆盖6请求并发同键重放、事务失败回滚、跨会话偏好和超出聊天窗口后的恢复。
- HTTP 固定回归集28个场景、35次请求，35次通过；29个返回方案全部满足脚本检查的费用公式及预算/配送约束。
- 该次串行请求耗时 p50 13.23ms、p95 35.52ms；本地规则路径模型调用0次，模型费用0美元。未计入基础设施费用。
- Java 20项测试全部通过（包含3项Testcontainers真实MySQL测试），验证全新库V1–V3迁移；既有演示库V2→V3升级也已完成。
- 真实Agent进程重启后同键返回原任务，下一轮仍保留区域和品类；[恢复记录](validation/local-life-recovery-20261021.json)标注了具体实验边界。
- Chromium实际页面验证通过：登录、报价拆分、需求显示和“改成2杯”多轮更新，未发现页面脚本错误。

原始HTTP报告：[local-life-evaluation-20261021.json](validation/local-life-evaluation-20261021.json)。这些都是开发者构造的固定回归数据，100%通过不代表真实语言任务100%成功，也不代表生产吞吐或P95承诺。

## 简历与下一轮优先级

可以描述：实现基于LangGraph的本地生活推荐演示，拆分商家、商品、配送工具，以完整到手价和送达时间作硬约束；使用MySQL事务与请求幂等支持任务重放，通过多轮、失败回滚和并发重复请求测试。数字必须注明评测范围，不能写成真实用户线上成绩。

下一轮最值得做：

1. 收集独立于开发者关键词的用户表达，构造留出集；衡量遗漏条件、错误放宽、错误澄清和成功率。
2. 将模型限定为结构化需求抽取，保留确定性费用和约束校验；比较规则基线与模型的准确率、耗时、费用。
3. 对工具添加受控超时、故障注入和远程适配；引入外部调用后再设计持久化执行与恢复，区分可重试读和有副作用操作。
4. 做少量真实试用并记录反馈；完善偏好删除、任务保留周期与生产身份接入后，才考虑公开部署。

不急于增加多Agent、RAG或更多框架。当前最有价值的面试讨论是“费用算对、硬约束不丢、重复请求不重复写、证据可复现”。
