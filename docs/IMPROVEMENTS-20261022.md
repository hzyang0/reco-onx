# 2026-10-22 实际使用问题修复

本轮重点是减少“看似完成需求，实际漏掉限制”的情况，保留小规模合成数据演示边界。

| 真实触发场景 | 原行为/风险 | 修改后的行为 |
| --- | --- | --- |
| 北区拿铁预算30元 | 拿铁被降成咖啡品类，可能返回更便宜的美式 | 商品名称作为硬约束，只返回燕麦拿铁，到手23元 |
| 下一轮预算改成20元 | 可能跨商品替代 | 保留拿铁限制，明确无结果；“不限款式”后才允许美式 |
| 两杯、三十五元、二十分钟 | 部分中文条件被忽略 | 支持带单位的0～99中文整数；超范围、模糊预算和未支持的时间表达要求澄清 |
| 同句出现两个区域或品类 | 默认取最后一个 | 明确询问选择，避免替用户决定 |
| 数据库运行在东八区 | UTC写入与默认时区读取混用，可能错判过期 | Python每条新连接设置UTC，MySQL TIMESTAMP读写和到期比较一致 |
| 明确重新保存一个已过期偏好 | 更新值但保留旧expires_at，仍不可用 | 明确偏好更新同时清除旧过期时间 |
| 会话超过50条消息后刷新 | 返回最早50条，最新需求不可见 | 取最近50条，再按时间正序展示 |
| 发出请求后立即新建会话/退出 | 旧WebSocket响应可能写入新界面 | 响应与发送时身份及会话绑定，过时响应不再渲染 |

商品名称为标题字面匹配，不是对商品成分或食安信息的推断。文本规则仍是有限解析器；无法识别所有未见表达。结构化参数支持明确 `product_query`，真实自然语言理解质量仍需独立留出集和用户试用。

## 仍然优先的演进方向

1. 用真实用户表达形成独立留出集，再引入受约束的模型抽取，比较遗漏条件、错误放宽、耗时和费用。
2. 增加真实地址、营业时间和报价更新时间等业务数据；先明确数据来源和工具契约，再接入外部配送接口。
3. 外部工具接入后增加故障注入、超时和有副作用请求的幂等；当前数据库事务重放不能直接当作远程任务自动恢复。
4. 面向真实部署再完善身份认证、数据保留与删除、监控告警。当前体验登录与合成库存不应包装成上线服务。
