# 初步项目评审与改进（2026-10-21）

> 本文保留首轮评审基线。后续已实现本地生活工具、完整报价、结构化会话和幂等任务；当前状态及验证结果见 [本地生活指南](LOCAL-LIFE-GUIDE.md)。下文“尚未完成”描述首轮时点。

## 结论：Agent 基础已具备，本地生活目标尚未完成

当前是 **带约束与会话记忆的推荐 Agent 工程原型**，工具后端是 goods/live/ad 三路推荐 DAG。已具备 LangGraph、受限模型规划、HTTP工具、MySQL/Redis和用户界面，但不能据此称为本地生活决策服务。

与 XPlanet 相比，reco-onx 的下一阶段更值得投入业务与评测：把候选召回真正变为围绕当前约束的决策工具，再引入商家、配送和到手价。通用问答、多 Agent、RAG 或更多前端动效都不是当前主线。

## 本轮确认的问题与修改

1. **不能为凑结果擅自改需求。** 删除无条件清空 `preferred_source` 的 relax 回路。无匹配时输出各条件排除计数，并保留来源、品类、预算与去广告条件；只有后续用户明确修改才更新。
2. **临时预算不能污染长期偏好。** 规划按长期偏好→最近用户消息→本轮条件覆盖；只有“记住／以后／长期偏好”且无临时标记才更新本轮字段。允许广告可写 false，不限预算可删除旧预算。
3. **预算检查不能将缺失价格当0或截断小数。** 缺失、非数字、负值、NaN价格均不满足预算约束；支持0预算与两位小数。当前预算只针对已知商品价格，未引入配送费用。
4. **模型输出需要应用层约束。** 用Pydantic限制字段、枚举、数值范围和布尔值；错误计划回退本地规划，当前可识别的明确条件不能被模型放宽。模型调用有超时并关闭SDK自动重试；真实模型的复杂语义理解仍需独立评测。
5. **会话隔离和恢复必须落到代码。** Redis键与SQL恢复查询同时包含userId/sessionId；先写MySQL；已有缓存才追加并裁剪到8条，缓存缺失则由完整审计窗口重建，避免只写入当前消息遮住旧上下文。移除跨轮内存checkpoint，每轮新建图状态，不让澄清或失败携带旧推荐。
6. **故障与指标可见。** 网络/数据库/Redis故障明确结束当前请求，返回 `tool_error`；记录 `elapsedMs`、模型调用次数与已观察到的token数。本地规划模型费用为0；外部调用费用返回null，不能用未知价格或缺失usage伪造账单。
7. **补上Agent自动化验证。** 添加Python回归测试和独立CI job，以及 `scripts/evaluate-agent.py`。评测按预设的用户约束独立验算，不复用Agent的过滤函数作为裁判。

## 尚未解决的重要边界

- 推荐后端只接收 `userId/scene/limit`，按历史画像召回20条后再过滤。本轮品类/预算未下推到召回，可能漏掉全库存在的可行商品；空结果只能说“本次候选不匹配”。
- 本地解析器覆盖有限中文表达，不是通用语言理解器；复杂否定、多个品类组合、未知地址/配送要求尚未完整识别。LLM参数验证不等于语义正确或提示注入全面防御。
- 最近8条消息可恢复，但临时约束尚无独立的结构化会话快照；超出窗口可能丢失。未实现同会话并发请求序列化和任务级幂等/断点续跑。
- 先写审计再更新缓存不是跨MySQL/Redis的原子事务；存储部分失败可能留下用户消息，重试也可能重复审计。不可宣称Exactly-once。
- HTTP `/api/chat` 和 `/api/memory` 仍是演示接口，选择画像不等于真实认证；公开部署前必须将HTTP/WS身份统一绑定服务端认证用户。
- 旧版本已经写入的长期偏好无法可靠判定是否为用户本意，本轮不自动清除用户数据；试用前应允许用户审阅、删除这些偏好。

## 后续路线：按简历价值排序

### P0：把约束处理做成可验证的能力

新增受限候选查询工具，显式接收品类、预算、位置和送达时限等结构化参数，区分硬约束、软偏好和来自哪一轮。优先解决召回遗漏和会话窗口丢约束；结果返回 `satisfied/unknown/violated` 和原因，不能静默忽略未支持的条件。

验收：当前需求与旧偏好冲突时以当前需求为准；缺价/缺配送信息不能算满足；不满足条件的候选不被推荐；已知可行数据不会因旧画像召回而遗漏。

### P1：完成一个小而真实的本地生活闭环

自建少量商家、商品和配送数据，明确数据来源、更新时间和演示属性。拆分 `search_merchants`、`search_products`、`quote_delivery` 的输入输出契约；不需要为此部署三个微服务。

用整数分计算 `商品价 + 包装费 + 运费 - 合法优惠`，校验起送价、服务范围、库存、到达时间及报价有效期。排序先保证所有硬约束，再比较到手价和软偏好。展示两三个方案的取舍；无解时只提出最小放宽建议，等待用户选择。

验收案例：商品价较低却因运费更贵、满减门槛未满足、超配送范围、报价过期、两条条件互相冲突、用户拒绝放宽条件。

### P1：形成能写进简历的评测与恢复证据

建立至少50个独立用例，按预算边界、位置、配送、费用、无解、多轮冲突、记忆清除、工具超时、报价过期和重启分组；开发集与保留集分开。分别报告有解任务成功率、无解判断正确率、硬约束违反率、澄清率、p50/p95、模型调用/token/已知单价成本，并保存错误案例。

任务恢复加入taskId、请求幂等键和明确终态。只对可重试工具错误在总超时预算内重试；完成结果可重放，中断任务可恢复或标为失败。用故障注入证明，不能仅以聊天记录仍在声称任务已恢复。

### P2：交付与试用

增加统一身份认证、用户可审阅的记忆管理和少量真实试用记录。以问题清单驱动迭代，暂缓通用聊天、RAG和多Agent扩张。

## 简历定位

目前建议标题：**约束驱动的推荐 Agent（LangGraph + Java 工具后端）**。可以讲受限规划、确定性约束校验、显式长期记忆、失败终止、跨存储恢复边界与可复现评测。

在商家/配送/完整到手价闭环完成前，不写“本地生活智能决策平台”或“已接入真实商家”。在完成独立评测前，不写“高成功率、低费用”等缺乏基准的效果结论。XPlanet可先作为后端主项目，这个项目完成P0/P1后再作为差异化Agent主项目。
