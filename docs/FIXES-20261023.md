# 2026-10-23：需求遗漏、商品匹配和CI修复

## 判断与实际影响

此前发现的预算、时限、饮食要求遗漏都是功能缺陷，不应被描述为可接受的正常误差。这些失败不能靠“规则模型能力有限”免除：识别不了应澄清，不能把未知当作没有要求。

本次修复包含：

| 问题 | 修改后的行为 |
| --- | --- |
| “只有十六块九”“十八元五角”“一百二十元” | 转换成整数分的到手总预算，保持小数精度 |
| “一刻钟”“一个钟头”“半小时” | 转换为15/60/30分钟；不把“20分钟后”“下午三点整”当作最长时限 |
| “多久送都可以” | 清除旧时限，保留预算、商品、区域等其余条件 |
| “燕麦拿铁”“牛奶面包组合” | 保留完整指称；组合商品不拆成两种商品 |
| 普通商品偏好与“只要” | 普通偏好允许单列同类替代；“只要/只喝/不能替换”不返回替代项 |
| “咖啡改成两杯，其他照旧” | 仅修改数量，同品类提及不清除已保存的完整商品名 |
| “两杯改成三杯”“不在北区，改送南区” | 识别明确更正；“一杯或两杯”“北区和东区之间”要求澄清 |
| 零乳糖、过敏、口味等缺少事实依据的要求 | 要求澄清，持久化待处理条件；“继续查询”不能绕过，旧任务重放/读取也不能绕过 |
| 撤回未接受的改口 | 明确撤回后恢复上一次已接受快照，不把被拒绝的商品变化混进去 |

## 完整匹配与替代推荐

`product_query` 保存完整商品名称。`product_match_mode` 为 `prefer`（默认）或 `exact`。

- `items` 只包含符合原商品要求的方案，按到手价、时间排序。
- `alternativeItems` 单独列出同类候选，仍必须满足预算、区域、数量和时限，每项标记 `requiresConfirmation=true`，不会自动修改原需求。
- 页面先显示原商品匹配，再显示“同类替代：未满足原商品名称，需明确选择”。
- 例如东区没有燕麦拿铁，会说明原需求无匹配，并单列17元的东区拿铁；说“只要燕麦拿铁”后不再给替代。
- 替代报价有同样的有效期校验；不得重放过期替代报价。

原种子中北区没有同时营业的第二款拿铁，因此“精确方案优先于更便宜的同类替代”还使用独立图测试夹具验证，而不为通过测试修改商家种子。

## 待澄清状态与升级

新增Flyway V4，在会话表添加 `pending_requirements` JSON列。启动Java后端先自动迁移，再启动新Agent；已有V1–V3迁移保持不变。

待处理饮食条件与任务/审计使用同一事务提交，按用户与会话隔离。普通追问不清除条件；只有明确撤回且没有新增不可验证要求才解除阻塞。已保存任务内容不被改写，但读取或重放时会根据当前待处理条件拒绝返回旧推荐。会话有效期默认24小时，过期后按会话失效规则处理。

如果第一次请求就包含不可验证条件，系统不会把该请求当作已接受需求；撤回后可能需要补充区域/品类。明确建立的长期偏好不因失败的临时改口而改变。

## CI截图：有什么影响、为什么、怎么处理

截图说明 `verify` 成功，而 `agent-policy` 和 `local-life-integration` 失败。它意味着Python策略检查和端到端验证未取得远端通过证据；不等于服务已经崩溃，也不能据Java成功就认为整个项目通过验证。启用必需检查的PR可能因此被阻止合并。

失败job都在2～3秒结束，共同使用 `actions/setup-python@v5`；成功job的Action全部已固定完整SHA。这个差异**高度符合仓库要求Action固定完整SHA、在初始化阶段拒绝可变标签的情况**，但截图没有Annotations正文，当前GitHub API日志读取仍返回403，因此尚不能确认唯一根因。

已做的修复：

- 两处setup-python固定到官方v5.6.0的完整SHA。
- upload-artifact固定到官方v4.6.2的完整SHA。
- SHA通过官方仓库引用核验，workflow通过actionlint检查；没有删除测试或设置忽略失败。
- 集成测试失败时保存Java/Agent日志和评测报告为 `local-life-verification` artifact。
- 修复后的33次语言挑战已转为回归门禁，与原有45次HTTP回归一起在CI运行。

推送会触发新运行。应查看最新运行而非历史失败邮件；如果仍失败，打开失败job的Annotations或第一个红色步骤，将具体错误用于继续定位。403是当前工具读取Actions状态的权限限制，与仓库中测试是否通过是两件事。未读取新运行结果前不能宣称远端CI已经绿色。
