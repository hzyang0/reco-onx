# 如何评测和组织真实试用

## 分清三种证据

| 方式 | 可以自行完成吗 | 能证明什么 |
| --- | --- | --- |
| 工程回归 | 可以，自动脚本和故障注入 | 已知规则、事务、费用、恢复是否正确 |
| 独立措辞挑战 | 可以，由不看实现和旧用例的测试作者出题 | 当前实现对未用于调试的表达有哪些盲点 |
| 真实用户试用 | 需要实际用户参与；可自行组织 | 用户是否知道怎么输入、能否理解冲突、是否愿意继续使用 |

模型生成语言样本和模拟用户都应标为合成测试。不能据此声称“已有真实用户试用”。本仓库挑战集由隔离实现信息的测试代理生成，仍受到同一模型生态、已提供业务范围和开发者标签复核的影响，不是统计独立的人类样本。

## 独立语言评测怎么做

1. 先冻结业务事实与评分标准：区域、品类、数量、商品名称、预算、时效，什么情况下应该澄清。标签按用户意图填写，不能迁就解析器。
2. 测试作者不看解析代码、旧测试和历史报告，以口语、同义表达、省略和多轮修改出题；实现者复核业务事实，记录任何标签修订。
3. 首次运行前保存文件及SHA256，评测用新会话。报告保存输入、预期、实际解析、返回商品、错误和耗时。
4. 分别计算整段任务成功率、请求成功率、实际返回商品对人工标签的约束满足率、澄清正确性。没有返回方案不能自动当作任务成功。
5. 看过失败并修改实现后，这套集就变成开发回归集；下一轮必须另收一份未使用的数据，不能把反复调到满分仍称为留出成绩。

```bash
python scripts/evaluate-language.py \
  --cases agent-service/evaluation/language_challenge_v1.json \
  --output output/language-challenge.json
```

只要有失败，脚本退出码为1，报告仍完整写入。首轮发现问题是评测的价值，不能删掉失败案例让结果变好。此挑战集暂不作为要求全绿的CI门禁；原有确定性工程回归仍要求通过。

费用分开记录：当前本地生活请求没有调用LLM，服务端模型费用为0；这不包括生成测试集所用的模型费用、人力、服务器。评测延迟是串行本地请求数据，不代表生产负载性能。

## 真实试用建议：先5～8人，每人15～20分钟

这是小样本探索性试用，目标是找问题，不是估算总体成功率。优先请未看过README和示例句的同学参加；技术和非技术背景都保留。第一批至少3人也可以，但如实报告人数与任务数。

准备：

- 在你自己的演示实例上运行；不要公开目前使用演示身份选择的服务。线下同一台电脑轮流体验或由你共享屏幕，让参与者自己措辞均可。
- 参与者知道这是合成商家数据和推荐演示，不会真实下单。不需要真实姓名、地址、手机号或付款信息；用P01、P02等编号。
- 每项任务新建对话，多轮任务在同一对话内进行。记录已有长期偏好；首轮不安排“记住以后”的任务。如果参与者主动改变了长期偏好，记录并使用另一干净体验身份继续，避免混入后续任务。
- 说明会记录输入与操作观察，参与者可以拒绝记录或中止。录屏另行征得同意；不用录屏也能完成。对外分享前检查聊天中的个人信息。
- 发给参与者 [任务卡](PARTICIPANT-TASKS.md)，主持人另外持有 [观察表与判分说明](OBSERVER-GUIDE.md)，不要提前展示答案。

执行：

1. 2分钟介绍能力边界，让参与者自行登录。
2. 10～15分钟完成任务卡，先不提示措辞。如果需要帮助，记录帮助发生的时点，不把帮助后成功算成“独立完成”。
3. 3分钟追问：哪处不理解、哪次不信任结果、现实中是否会再用、最缺少什么。
4. 把观察录入 [空白CSV表](feedback-template.csv)，只填真实观察，不预填成功率。

结束后计算：独立完成任务数/尝试任务数、需要主持人帮助的次数、约束违反次数、无效澄清次数、每任务耗时中位数。一个参与者多项任务不是多个独立用户；同时报告人数和任务数。满意度逐人列出，5～8人的均分不能包装成稳定用户口碑。

修复顺序：先修错误放宽和错误商品，再修无法完成的常见表达，再修解释和页面问题。第一批反馈用于改进，第二批新参与者验证是否改善。不要把同一人重复测试当作新增用户。

## 可以交给助手做什么

助手可生成隔离用例、编写检查器、调用本地接口、模拟操作/故障、整理匿名记录和定位失败。你把真实试用记录提供后，助手可归类原因、统计分母、生成改进清单。招募参与者、获取真实回答、实际满意度和使用意愿需要真实参与者产生，不能由助手代写。
