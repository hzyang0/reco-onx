## 1. 面试目标与优先级

优先掌握：Java 集合与并发、MySQL 索引与事务、Spring 事务边界、HTTP/TCP、两个项目的真实性与可靠性、常见算法。其次是缓存一致性、消息幂等、银行业务常识、JVM 排障。分布式共识细节和复杂模型训练不宜挤占核心准备时间。

专业回答采用四步：先给结论；解释机制；举项目中的具体例子；指出边界和代价。比如回答“怎么防止重复预约”，应说用户请求键负责幂等、设备行锁协调并发、槽主键保护排他，而不是只说“加锁”。

银行研发准备应重视正确性、可审计性、数据保护和故障恢复。这是岗位相关的工程判断，不是对该中心评分标准的断言。不要把银行研发理解成只有维护工作，也不要臆测其一定采用某种技术栈。

## 2. 自我介绍与项目陈述

### 2.1 一分钟模板

“各位面试官好，我叫【姓名】，来自【学校及专业】，研究方向是【真实方向】。我主要准备 Java 后端开发，并做过两个项目：实验设备预约平台 XPlanet，以及本地生活推荐服务 reco-onx。前者重点解决时间冲突、候补调度和事务一致性；后者重点解决多轮约束、工具报价和任务幂等恢复。我通过数据库集成测试、模拟用户竞争和故障恢复验证这些设计。希望在银行研发场景继续提升对业务正确性、可靠性和工程协作的理解。”

所有方括号必须替换成真实信息。不了解的研究成果、排名、奖项、用户规模不要添加。项目含协助开发时，应能说明自己实际设计、阅读、验证和修改的部分；不能把生成或协助完成的工作虚构成独立线上经历。

### 2.2 XPlanet 两分钟版本

用户申请某设备的半小时时间段，资源冲突时进入候补；取消后发限时补位资格，用户接受后确认或待审批。核心是设备行锁与槽唯一键，预约状态、审计和通知事件在同一事务内保存。后台处理超时与通知；同键重试能找回原预约。

可展开的难点：为什么待审批也占槽；为什么老候补会阻挡重叠的新请求；为什么原子改期不能拆成两个接口；同库 Outbox 如何恢复。已验证的是本地模拟和测试，不是实际实验室规模运营。

### 2.3 reco-onx 两分钟版本

用户给出区域、商品、预算、时限和数量，工具查商家、商品、配送规则，计算完整到手价并执行硬约束。当前本地生活主路径是有限规则加 LangGraph，不调用大模型。有效约束、未解决饮食要求、任务结果和对话保存到 MySQL；同键同内容重试重放结果，报价过期重新询价。

可展开的难点：省略字段与显式清除的差别；完整商品名与同类替代分离；为什么标题不能证明零乳糖；为什么任务重放不是恢复图的执行栈。Java 推荐 DAG 是另一条保留路径，不能画成每次本地生活查询必经的链路。

## 3. Java 基础、集合和异常

### 3.1 equals、hashCode 与对象相等

`==` 对基本类型比较值，对引用比较是否同一对象；equals 表达逻辑相等，默认实现仍是引用比较。相等对象必须有相同 hashCode，相同 hashCode 不保证 equals。重写 equals 通常必须配套重写 hashCode。

HashMap 先定位桶，再比较键。键放入后如果参与哈希或相等判断的字段改变，可能在原位置却无法用新哈希找到。工程上优先使用不可变键。项目中的 userId、设备 ID、请求键比可变业务对象更适合做键。

### 3.2 String 为什么不可变

String 的内容不能通过其公开 API 原地修改，便于共享、作为 Map 键和缓存哈希。变量重新赋值不等于原字符串改变。频繁循环拼接适合 StringBuilder；StringBuffer 的同步不能代替整个复合业务操作的并发控制。String 不可变也不代表包含密码的 String 能主动擦除内存。

### 3.3 集合对照

| 类型 | 主要特征 | 常见取舍 |
| --- | --- | --- |
| ArrayList | 连续引用数组，随机访问 O(1)，尾部追加均摊 O(1) | 中间插入／删除搬移 O(n) |
| LinkedList | 双向链表 | 找到位置仍需遍历，额外节点内存，不能笼统说插入总更快 |
| HashMap | 哈希桶，平均查找 O(1) | 不保证有序，不支持并发安全写 |
| TreeMap | 红黑树，排序及近邻查询 O(log n) | XPlanet 合并候补阻塞区间可使用 |
| LinkedHashMap | 维护迭代顺序，可选访问顺序 | 可用于有界本地 LRU 的构件 |
| ConcurrentHashMap | 并发 Map | 多次调用组成的业务事务仍不自动原子 |
| ArrayDeque | 双端队列 | 栈、队列常用；不允许 null |

Java 8+ HashMap 桶冲突多时可能树化，但需要同时满足容量条件。常见阈值树化 8、反树化 6、最小树化容量 64，属于实现细节，不是所有版本和 Map 实现的通用契约。面试应先解释冲突、扩容和线程安全，再补数字。

ConcurrentHashMap 的 `get` 后 `put` 组合仍可能竞争，优先考虑 putIfAbsent、compute 等合适原子 API。映射回调不要放慢外部调用。它不能保护数据库跨实例的设备占用。

### 3.4 泛型、重载、重写

重载在同一可见范围内方法名相同而参数不同，按编译期可见类型选取；重写是子类替换父类实例方法，体现运行时多态。返回类型本身不能单独构成重载。

Java 泛型主要采用类型擦除，`List<String>` 与 `List<Integer>` 不能靠运行时泛型实参直接区分。`? extends T` 适合读取 T，难以安全加入具体值；`? super T` 适合写入 T，读取通常只能当 Object。记忆法 PECS 要配合读写类型解释，不能只背缩写。

### 3.5 异常与资源

checked exception 编译期要求捕获或声明；RuntimeException 属于 unchecked。异常应携带可定位语义，在边界转换，不能到处 catch 后返回成功。try-with-resources 自动关闭 AutoCloseable，关闭异常可能作为 suppressed exception 保存。

`finally` 通常执行，但进程被强制终止等情况不能保证；finally 中 return 会掩盖原返回或异常，应避免。数据库连接归还、线程池关闭和日志记录都要注意异常路径。

### 3.6 常见追问

- Integer 比较为什么有时 == 为真？自动装箱缓存影响引用复用，业务比较值用 equals 或拆箱，并处理 null。
- final 是否线程安全？final 限制引用再赋值，不让引用对象自动不可变，也不保护复合操作。
- 深拷贝与浅拷贝？浅拷贝共享嵌套可变对象，深拷贝复制相应对象图；不能无脑用序列化替代清晰模型。
- 反射用途与代价？框架绑定、注入、序列化等；有访问控制、封装和性能成本，不应把反射说成无限绕过模块限制。

## 4. 并发、线程池、锁和异步

### 4.1 三个概念

原子性：一次操作不能被观察为中间状态。可见性：一个线程写入能被另一个按规则观察。顺序性：执行和可见顺序受 Java 内存模型约束。`volatile int count; count++` 有可见性但不是原子递增。

happens-before 描述可见性与有序性的约束，不是简单的墙上时间先后。常见关系包括监视器解锁先于后续同锁加锁、volatile 写先于后续同变量读、线程启动与 join 的相关规则。

### 4.2 synchronized 与 ReentrantLock

两者都可重入并提供互斥与相应内存语义。synchronized 随作用域自动释放；ReentrantLock 需要 finally unlock，可支持中断获取、限时获取、公平选项和多个 Condition。公平锁不等于 CPU 调度绝对公平，吞吐也可能降低。

锁粒度应保护不变量。锁住单次 Map 调用不能保护“查询空闲后插入”；Java 锁只在单进程内有效。XPlanet 多实例的共享事实在数据库，用设备行锁与唯一槽约束协调。

### 4.3 CAS、ABA 与原子类

CAS 比较预期值，匹配才更新；竞争高时重试成本增加。ABA 指值从 A 到 B 又回 A，单看值无法发现中间变化，可用版本号辅助。AtomicInteger 适合原子计数，LongAdder 适合高竞争统计，但其 sum 不是任意并发时刻的严格事务快照。

不要把 CAS 当作复杂转账事务的替代；账户余额、流水、状态需要一起提交，单字段原子更新不够。

### 4.4 线程池执行顺序

一般过程：线程数小于 corePoolSize 时尝试创建核心线程；否则尝试入队；队列满时尝试扩到 maximumPoolSize；仍无法接受则拒绝。不是先扩到最大线程再排队。

参数还包括 keepAliveTime、工作队列、ThreadFactory、拒绝策略。无界队列常使 maximumPoolSize 很难发挥预期作用，并可能积压内存。固定线程池默认队列并不等于严格有界。

拒绝策略：AbortPolicy 抛异常；CallerRunsPolicy 让调用方执行以形成反馈，但可能阻塞请求线程；Discard 丢弃、DiscardOldest 丢旧任务，不适合未经业务设计的关键金融操作。

线程数不能只背 CPU核数+1。先区分 CPU／I/O、数据库连接池、外部限流与延迟目标，再测量。增加线程可能让数据库更拥堵。

### 4.5 死锁与取消

死锁条件包括互斥、持有并等待、不可抢占、循环等待。统一加锁顺序是常用预防方式；XPlanet 用户锁在设备锁之前，多设备扩展可按 ID 排序。锁超时和事务回滚是故障处理，不是证明死锁不可能。

interrupt 是协作式中断。捕获 InterruptedException 后常需要恢复中断标记或按上层协议结束。Future.cancel(true) 不能保证 JDBC 或远端副作用立即停止。reco Java DAG 还要依靠连接和 socket 超时。

### 4.6 ThreadLocal

ThreadLocal 为线程保存独立上下文，并不自动跟随异步任务。在线程池中必须考虑任务结束 remove，避免上下文污染和对象滞留。传用户身份到异步线程要显式传播并清理，不能依赖偶然同线程执行。

### 4.7 适合项目的深问

“为什么 DAG 使用总截止时间？”因为每次等待都从同一 deadline 计算剩余预算，避免三个工具各等 500ms 导致总耗时远超 500ms。“为什么用完成队列？”按实际完成接收结果，避免先等待一个慢任务挡住其他已完成任务。

“Python async 是否让数据库自动不阻塞？”不会，同步 PyMySQL 仍会阻塞，项目用 asyncio.to_thread 执行同步事务；工作线程和连接仍有容量上限。

## 5. JVM、内存与排障

堆保存大多数对象；虚拟机栈保存线程方法调用帧、局部变量等；方法区是规范概念，HotSpot 常用元空间承载类元数据；运行时常量池属于相关类元数据结构，字符串驻留等实现不要混为一谈。程序计数器属于线程。

对象是否回收主要根据可达性分析，不是简单引用计数。GC Roots 包括活动线程栈相关引用、静态字段等。强、软、弱、虚引用具有不同回收与引用处理语义，缓存不要把软引用当确定的容量控制。

年轻代／老年代是常见分代思路，具体回收器布局不同。G1 使用区域、并发标记和混合回收，目标暂停时间是目标而非硬保证；不能声称完全没有 Stop-The-World。选择回收器应结合 JDK、堆大小、延迟与吞吐。

### 5.1 常见故障路径

| 症状 | 排查方向 |
| --- | --- |
| CPU 高 | 热点线程、死循环、频繁 GC、锁竞争与自旋 |
| 响应慢但 CPU 低 | 数据库锁、连接池等待、外部 I/O、队列积压 |
| 内存持续升高 | 合理缓存增长还是对象泄漏；分析保留链 |
| 栈溢出 | 深递归、无结束条件、异常循环调用 |
| OOM | 堆、元空间、直接内存或线程资源等具体类型 |

排障先确认时间窗口、版本变化和请求特征，再结合指标、线程栈、GC 日志、堆转储。不要未经评估就对生产高负载进程抓巨大 dump 或重启；先保全必要证据、控制影响。

项目关联：reco 候选上限、防止队列无限堆积；XPlanet 候补队列规模、占锁时长和分页扫描。数据库等待不能通过盲目增堆解决。

## 6. Spring、事务与接口工程

IoC 容器管理对象创建和依赖，DI 是注入依赖的方式；AOP 用于事务、日志等横切逻辑。构造器注入让必需依赖显式且容易测试。单例 Bean 默认被多个请求共享，成员可变状态需要并发设计，单例不等于线程安全。

### 6.1 @Transactional 高频追问

声明式事务通常依赖代理。外部通过代理调用时拦截，同类自调用不会重新经过代理。XPlanet reschedule 内调用 create 仍参与已经存在的外层事务，因此不能机械回答“自调用一定没有事务”。

默认对 RuntimeException 和 Error 回滚，checked exception 是否回滚取决于配置。吞掉异常、在异步线程另起数据库操作、错误事务管理器、非代理对象都会改变预期边界。事务方法返回正常不代表所有外部副作用都能回滚。

传播：REQUIRED 加入现有事务或新建；REQUIRES_NEW 暂挂外层并建立独立事务，可能额外占连接且独立提交；NESTED 常依赖保存点及事务管理器支持，不应等同于新独立事务。

只读事务是提示／优化约定，不应视为所有数据库上的绝对写入禁止。大事务增加持锁时间、回滚成本和连接占用。

### 6.2 REST 与错误处理

GET 应无业务写副作用；POST 常用于创建或动作；PUT 表达替换／更新语义，幂等性由业务实现支撑，不能只看方法名。400 参数不合法；401 未认证；403 无权限；404 不存在；409 状态或幂等冲突；429 限流；5xx 服务故障。

DTO 校验格式，Service 校验动态规则，数据库约束保护最终事实。前端隐藏按钮不是授权。错误提示应有业务含义，日志保留定位信息但避免泄漏密钥、身份证号等敏感数据。

### 6.3 Session 与 JWT

服务端 Session 可集中撤销，访问依赖存储；JWT 可离线验签，但过期前撤销需要额外机制，并要校验算法、issuer、audience、时间等。JWT payload 通常只是编码，不默认加密。

XPlanet 使用随机 token 的摘要落库，不是 JWT。reco 是演示画像登录，不能包装成生产 SSO。面试问“能上线银行吗”应说明需要生产身份、权限、审计、数据治理与运维流程。

## 7. MySQL、索引、事务和锁

### 7.1 索引与 B+ 树

B+ 树内部节点主要保存导航键，叶子保存索引记录；较高扇出降低树高，叶子组织有利范围访问。InnoDB 主键是聚簇索引，二级索引叶子携带主键，查询未覆盖列可能回到聚簇索引。“回表”不是回磁盘的同义词，相关页面可能在缓存。

联合索引通常按列顺序排序。左前缀、等值后范围、排序与覆盖需要结合具体 SQL；不要说索引遇到范围后所有后续列完全无用，它们仍可能参与过滤或覆盖等优化。

覆盖索引减少回表，但宽索引增加写入与存储成本。索引不是越多越好。小表、低选择性、大量返回行时优化器可能不用索引。

常见不利情况：前导通配符 LIKE、对索引列施加不匹配函数、隐式类型转换、不同字符集／排序规则。是否实际使用，要看执行计划和实际数据，不能只背“索引失效”列表。

### 7.2 ACID 与日志

原子性：事务整体提交或回滚；一致性：业务不变量在合法事务中维持；隔离性：并发可见性与冲突规则；持久性：提交数据按配置与故障模型持久保存。

undo 参与回滚和旧版本读取；redo 支撑崩溃恢复；binlog 记录服务层逻辑变更，用于复制与恢复等。redo 和 binlog 不是同一种日志。提交持久性与刷盘策略、存储可靠性有关，不能说任何断电都绝对零丢失。

### 7.3 隔离级别与 MVCC

读未提交可脏读；读已提交避免脏读但可不可重复读；可重复读提供更稳定快照语义，锁定读还涉及范围锁；串行化限制更强、并发代价更高。不能仅凭级别名称就断言所有 SQL 的实际锁行为。

InnoDB 一致性读借助版本链和 Read View。RC 通常每次一致性读建立新视图，RR 通常在事务首次一致性读后复用视图；锁定读 SELECT FOR UPDATE 属于当前读语义，不能与快照读混淆。

幻读讨论必须说清快照读还是当前读、是否加锁、索引范围。面试不宜只答“MVCC 完全解决所有幻读”。

### 7.4 记录锁、间隙锁和死锁

记录锁保护索引记录，间隙锁保护一定范围的插入空隙，next-key 结合两者。具体采用哪些锁与隔离级别、索引、谓词及执行计划有关。无合适索引会扩大扫描和锁影响，不能简单说“没有索引就必然表锁”。

XPlanet 主动锁设备行，再检查槽；这避免把正确性完全寄托在复杂区间查询的间隙锁行为上。槽主键(equipment_id,slot_at)才是最后排他边界；(equipment_id,start,end)唯一键无法阻止部分重叠。

### 7.5 乐观锁与悲观锁

悲观锁在读取／修改前协调排他；乐观锁通过版本或旧值条件 UPDATE 检测冲突。乐观并非不加任何数据库锁，UPDATE 执行仍会涉及锁。高冲突下反复重试未必更快。

XPlanet 管理员 expectedVersion 防止旧页面覆盖新修改，即使已有设备行锁，仍需要表达用户编辑版本。状态更新 WHERE status=旧状态防止非法转移。

### 7.6 SQL 纸上题

同设备区间相交：

```sql
SELECT id FROM reservation
WHERE equipment_id = ?
  AND start_at < ? /* 新结束 */
  AND end_at > ?;  /* 新开始 */
```

边界相等不冲突，左闭右开。实际还要限定活动状态并配合事务锁；这条查询本身不防并发抢占。

用户最近三笔记录（MySQL 8 窗口函数示例）：

```sql
SELECT user_id, id, created_at
FROM (
  SELECT user_id, id, created_at,
         ROW_NUMBER() OVER (
           PARTITION BY user_id ORDER BY created_at DESC, id DESC
         ) AS rn
  FROM reservation
) t
WHERE rn <= 3;
```

GROUP BY 聚合会折叠行，窗口函数可保留每行。ROW_NUMBER 每行唯一序号；RANK 同名次后跳号；DENSE_RANK 不跳号。

分页若 offset 很大，考虑基于有序唯一键的游标分页；需要稳定排序和合理边界，不要用不稳定时间字段单独作为游标。金额求和注意单位、NULL 与溢出。

## 8. Redis、缓存与分布式协调

### 8.1 常用类型和过期

String 用于计数、简单缓存；Hash 用于字段集合；List 用于顺序列表；Set 去重；Sorted Set 按分数排序。类型选择要跟访问模式匹配。大 key、热点 key 和批量阻塞操作会影响延迟。

Redis 命令执行模型常被简称单线程，但网络、持久化与后台任务随版本存在多线程／子进程协作，不能笼统说 Redis 只有一个线程。过期删除与内存淘汰是不同机制。

RDB 是快照，AOF 追加记录写操作；各有恢复速度、体积和丢失窗口取舍。复制通常不是同步强一致提交，故障切换可能涉及丢失窗口。

### 8.2 三类缓存问题

穿透：持续查不存在数据，可用空值缓存、布隆过滤器配合源数据校验；布隆有假阳性，不能当最终存在性事实。

击穿：一个热点键失效后大量访问回源，可互斥重建、提前刷新、按业务接受逻辑过期。

雪崩：大量键同时失效或缓存整体故障，可错开 TTL、限流降级、隔离回源压力。不是加随机过期就解决缓存宕机。

### 8.3 数据库与缓存一致性

常见 Cache Aside：读缓存未命中读库并回填；更新先改库再删缓存。这样仍有并发与删除失败窗口，不是强一致保证。可用重试、事件驱动失效、版本校验和短 TTL；严格余额、授权、预约排他应以数据库事实为准。

延迟双删也不保证任意网络和时序下绝对一致。回答应先明确业务允许的陈旧时间，再选方案。

### 8.4 分布式锁

常见思路 SET key randomValue NX PX timeout，解锁用原子比较 owner 后删除。不能先 GET 再 DEL，否则中间可能误删新持有者的锁。

但租约过期后旧执行者可能仍继续工作；需要 fencing token 或资源端版本判断等机制防止过期持有者写入。续期不是所有故障的答案。XPlanet 不需要为了简历把数据库行锁换成 Redis 锁。

## 9. 网络、安全和操作系统

### 9.1 TCP 与 HTTP

TCP 提供有序可靠字节流，不保留应用消息边界；HTTP 定义请求／响应协议。三次握手建立双方序号与通信状态，四次挥手是常见独立关闭流程，实际报文可能合并，不能机械要求每次四包。

TIME_WAIT 帮助处理迟到报文及可靠关闭，通常与主动关闭方相关。连接建立成功不代表对方业务已经处理成功；超时也不证明业务没有提交，这正是项目需要幂等键的原因。

HTTP/1.1 可持久连接；HTTP/2 多路复用流，但底层 TCP 丢包仍可能影响同连接；HTTP/3 基于 QUIC。HTTPS 在 HTTP 上使用 TLS 保护传输，证书验证身份，密钥协商与对称加密配合，不是每条业务数据都用公钥直接加密。

### 9.2 从输入网址到页面

缓存／DNS 解析 → 建连接 → TLS（HTTPS）→ HTTP 请求 → 服务端路由、认证、业务和数据库 → 响应 → 浏览器解析 HTML/CSS/JS。需要说清缓存、连接复用等可能跳过部分步骤。慢接口排查按 DNS、连接、服务排队、应用、数据库、传输分层，不只看 Java 耗时。

### 9.3 安全区别

XSS 是不可信内容被当脚本执行，按输出上下文编码、避免危险 HTML 注入，CSP 提供额外防线。CSRF 利用浏览器自动带身份凭证发起非预期请求，需 token、SameSite、来源校验等适合方案。CORS 是浏览器跨源读取规则，不是后端权限系统。

SQL 注入通过参数化查询处理值；动态表名／排序字段通常不能普通占位符绑定，要白名单。防重复提交不是防越权，知道 reservationId 不意味着有权操作。

密码用慢哈希加盐，如 BCrypt；高熵随机 token 可存摘要。加密可解密，哈希通常不可逆；Base64 是编码，不是加密。日志脱敏必须考虑搜索、备份和导出链路。

### 9.4 操作系统常识

进程有独立地址空间；线程共享进程资源并有各自执行栈，切换与同步成本不同。用户态／内核态隔离权限，系统调用跨越边界。虚拟内存让进程看到自己的地址空间，缺页不一定都是错误，也可能触发装入。

I/O 多路复用让一个线程管理多个就绪连接；epoll 不等于业务处理不阻塞。文件描述符、socket、线程数和连接池都可能耗尽。出现“连不上”要区分拒绝、超时、DNS 失败和应用返回错误。

## 10. 银行场景：正确性、可审计与可靠性

以下是准备用的通用工程场景，不是农业银行内部系统设计说明。

### 10.1 转账为什么不是两个余额 UPDATE

一个数据库内可用事务同时处理扣款、入账、流水、业务请求状态。检查币种、余额、账户状态、金额正数、业务权限和风控结果。账户锁按稳定顺序获取，避免 A→B 和 B→A 循环等待。金额用整数最小单位或明确精度的十进制，不用 double 表示财务金额。

教学性伪代码：

```text
开始事务
按账户 ID 顺序锁定转出、转入账户
检查 requestId：存在且内容相同 → 返回原业务结果
校验币种、账户状态、金额与可用余额
扣减转出，增加转入
插入带唯一业务标识的流水和请求结果
提交事务
```

这只是本地事务思路，真实银行还涉及账务规则、授权、清算、限额、反洗钱、对账和审计。不能据此声称自己实现了银行核心。

### 10.2 跨系统转账如何考虑

两个服务不同数据库不能靠单库事务原子提交。先定义业务状态，如受理、处理中、成功、失败、待核实；用幂等接口、可靠事件、超时查询、补偿和对账推进。超时应可能返回“处理中”，而不是贸然认定失败再重复扣款。

补偿不是时光倒流。已发生的外部动作可能无法直接撤销，需要反向业务记录。Saga、TCC、事务消息都需要实际参与方契约，不是选一个名词就获得强一致。

### 10.3 幂等、防重、对账的差别

幂等：同业务请求重复执行收敛到规定效果；防重：识别重复调用并抑制；对账：比较不同记录或系统的事实，找出差异并处理。三者互补。

请求键需要作用域、唯一约束、内容校验与状态结果；不能只靠前端禁用按钮。XPlanet 比较设备／时间／用途，reco 比较 payload 指纹，都可迁移这种思路。

### 10.4 消息可靠性

业务与 Outbox 同事务，消费者按事件 ID 去重；消费落库与确认顺序决定崩溃窗口。外部消息系统不能和本地库自动共享原子提交，常见设计接受至少一次并实现业务效果幂等。

失败要有重试上限、退避、隔离、人工处理和审计。无限重试会扩大故障；直接丢弃可能漏业务。XPlanet 当前是同库站内信，不是已经接了 Kafka／RabbitMQ。

### 10.5 可用性、容灾、数据保护

RTO 是恢复所需时间目标，RPO 是可接受的数据损失窗口目标。备份不等于高可用，副本不等于备份；误删除也可能同步复制。需要恢复演练、权限控制和变更审计。

最小权限、职责分离、敏感字段保护、留痕与可追溯是通用原则。涉及具体监管要求时，应以适用制度和正式规范为准，不编造条款号、年限或内部标准。

性能优化不能牺牲正确性。出现重大不确定状态先保护业务事实、定位与止损，再恢复服务；不为追求“接口全成功”把失败吞掉。

### 10.6 金额为什么不能直接用 double

二进制浮点不能精确表示许多十进制小数，例如 0.1。因此金额通常采用有范围约束的整数最小单位，或明确精度和舍入规则的 BigDecimal／数据库 DECIMAL。reco 用整数分计算到手价；这适合当前人民币商品报价，但不能直接推导出它实现了多币种、汇率和计息。

```java
static java.math.BigDecimal payable(String unitPrice, int quantity) {
    if (quantity <= 0) throw new IllegalArgumentException("quantity");
    java.math.BigDecimal unit = new java.math.BigDecimal(unitPrice);
    if (unit.signum() < 0) throw new IllegalArgumentException("price");
    return unit.multiply(java.math.BigDecimal.valueOf(quantity))
        .setScale(2, java.math.RoundingMode.HALF_UP);
}
```

这里从十进制字符串构造，先乘后统一舍入；这是演示约定，不是所有银行业务的通用规则。业务可能要求逐项舍入、累计后舍入或不同币种小数位，必须在合同和需求中明确。`new BigDecimal(0.1)` 会带入二进制浮点误差；`BigDecimal.valueOf(0.1)` 使用标准字符串转换，但也不能修复此前已经发生的浮点计算误差。

`new BigDecimal("1.0").equals(new BigDecimal("1.00"))` 为 false，因为 equals 比较数值及 scale；compareTo 返回 0，适合纯数值大小比较。除法可能无限循环，必须明确精度／舍入策略。整数分也有溢出风险，可用有界输入、long、精确运算检查控制，不能认为整数天然安全。

### 10.7 余额、可用余额、冻结与流水

账面余额与可用余额可能不同：有冻结资金时，账面有钱也未必允许全额转出。面试设计应先明确透支、冻结、手续费、币种、营业日期和交易限额，不能简单写 `balance >= amount` 就宣称满足银行转账需求。

流水记录交易事实；余额是账户状态；对账验证不同账务视图是否一致。复式记账需要借贷平衡及明确科目模型，普通的“加一条日志”不等于实现了复式账务。冲正应产生可追踪的关联记录，并遵守状态与权限，不能删除原流水掩盖历史。上述是业务建模讨论，两项目都不是核心账务系统。

### 10.8 CAP、最终一致性、限流与熔断

CAP 中 C 是线性一致性，A 是理论上的请求可获得非错误响应要求，P 是网络分区。发生分区时，无法同时保证该定义下的 C 和 A；不要说任何系统都可以随意“三选二”，也不要把 C 等同于 ACID 中业务约束一致性。银行系统也不能笼统贴一个 CP 标签，应区分账务写入、历史查询、通知等操作。

最终一致性需要收敛机制：重试、幂等、持久化状态、补偿、对账和人工处置。“异步发消息”本身不保证最终成功。账户扣款不能用没有补偿边界的异步覆盖；通知延迟通常可以接受。选择取决于具体业务不变量。

限流控制进入系统的速率；并发隔离控制占用资源的数量；超时限制等待；熔断在持续失败时暂时阻断对故障依赖的调用；降级提供明确的受限能力。令牌桶允许有限突发，漏桶偏向平滑输出。线程池队列不是无限容量的保险箱，排队超过请求截止时间只会消耗资源。重试需上限、退避和抖动，并只针对适合重试的操作，避免各层同时重试造成请求倍增。

### 11.1 Agent 追问

“为什么不是普通规则系统？”可以承认主路径是受约束工作流，Agent 工程价值在工具边界、状态、验证、恢复和评测；不要为名词夸大自治能力。

“模型 hallucination 怎么办？”当前主路径不调用模型；未来模型只做结构化抽取或辅助规划，价格和库存来自工具，金额由确定性代码算，未知过敏原不能凭模型常识保证。

“RAG、微调、Function Calling 有何区别？”RAG 提供检索到的外部上下文；微调改变模型参数或适配行为；Function Calling 输出工具调用结构，由应用校验并执行。模型声明调用工具不代表工具已执行或业务已成功。

“如何评测？”独立预期字段、任务状态、商品事实、算式、时限和有效期；不要用模型丢失约束后的 intent 给自己判分。已修案例变成回归集，需继续保留新措辞留出集。

“怎么控制费用？”记录实际调用次数、输入输出 token、适用价格与缓存口径；不要把本地规则路径零模型调用说成整个系统零成本。

### 11.2 三层追问练习

问：为什么用数据库锁？答：共享资源事实在数据库，锁与状态提交同一事务。
追问：有唯一键还需要锁？答：唯一槽保护排他，但候补公平、资格、停用与状态变更需要协调。
再追问：热点怎么办？答：测锁等待、缩短锁内工作、按资源分区；引入更细粒度策略前重新证明不变量。

问：为什么保存结构化快照？答：聊天文本会截断并混入建议，快照明确有效约束。
追问：并发两轮？答：同会话锁串行更新。
再追问：跨会话偏好冲突？答：当前可能最后写覆盖，未来需版本或用户维度更新协议；不能宣称已经解决。

## 12. 编程实操：解题流程、模板和边界

语言和环境尚未由截图确认。以下用 Java 准备，重点是方法正确、复杂度和测试意识，不依赖特定平台模板。

### 12.1 每题固定流程

先确认输入输出和规模；列出空值、重复、负数、溢出；给朴素解；再说明优化依据；写代码；手算普通、边界、极端三个样例。不要一看到题就背模板，尤其要确定区间开闭、排序是否允许修改原数组。

### 12.2 哈希：两数之和

```java
static int[] twoSum(int[] a, int target) {
    java.util.Map<Long, Integer> seen = new java.util.HashMap<>();
    for (int i = 0; i < a.length; i++) {
        long need = (long) target - a[i];
        Integer j = seen.get(need);
        if (j != null) return new int[]{j, i};
        seen.put((long) a[i], i);
    }
    return new int[]{-1, -1};
}
```

先查后放，避免同一下标用两次；重复值仍可匹配。用 long 做差，避免 int 极端值溢出。平均时间 O(n)，空间 O(n)。本模板约定无解返回 -1，真实题要遵守题面。

### 12.3 二分：第一个大于等于目标的位置

```java
static int lowerBound(int[] a, int target) {
    int left = 0, right = a.length; // 搜索区间 [left, right)
    while (left < right) {
        int mid = left + (right - left) / 2;
        if (a[mid] < target) left = mid + 1;
        else right = mid;
    }
    return left;
}
```

前提数组升序。循环不变量：答案始终在候选边界范围内。结果可能为 length，表示没有满足元素。测试空数组、全小于目标、目标重复、首尾命中。时间 O(log n)，空间 O(1)。

### 12.4 栈：括号匹配

```java
static boolean validBrackets(String s) {
    java.util.Deque<Character> stack = new java.util.ArrayDeque<>();
    for (char c : s.toCharArray()) {
        if (c == '(' || c == '[' || c == '{') stack.push(c);
        else if (c == ')' || c == ']' || c == '}') {
            if (stack.isEmpty()) return false;
            char open = stack.pop();
            if ((c == ')' && open != '(') ||
                (c == ']' && open != '[') ||
                (c == '}' && open != '{')) return false;
        } else return false; // 本模板约定只允许括号字符
    }
    return stack.isEmpty();
}
```

不是左括号数量等于右括号就合法，顺序和类型都要匹配。时间 O(n)，空间 O(n)。空串在该约定下合法。

### 12.5 区间：半开区间冲突

```java
static boolean hasOverlap(int[][] intervals) {
    java.util.Arrays.sort(intervals,
        (a, b) -> Integer.compare(a[0], b[0]));
    for (int i = 1; i < intervals.length; i++) {
        if (intervals[i][0] < intervals[i - 1][1]) return true;
    }
    return false;
}
```

假设每个区间 start < end，且允许原地排序。按开始排序后检测相邻重叠即可发现任意冲突；等号表示首尾相接，不冲突。排序 O(n log n)，扫描 O(n)。它只是内存批量检查，不能直接替代数据库并发控制。

### 12.6 必须会讲的其他类型

- 滑动窗口最长无重复子串：维护当前窗口内字符位置，左边界只前进；Java char 是 UTF-16 单元，题面若要求完整 Unicode 字符需按码点处理。
- 链表反转：prev、cur、next 三引用；保存 next 后再改 cur.next。时间 O(n)，额外空间 O(1)。
- 快慢指针检测环：快走两步慢走一步，相遇说明有环；判断 next 是否为 null。
- 二叉树层序遍历：队列，每轮记录当前层 size；DFS 递归注意深树栈溢出。
- Top K：大小为 K 的小根堆维护最大 K 项，O(n log k)，边界 k=0、k>n 和重复值需约定。
- BFS 最短路：适用于无权／等权边；非负权一般考虑 Dijkstra，负权不能直接套。
- 动态规划：先写状态含义、转移、初值、遍历顺序，再压缩空间；不要只背结果公式。
- 零钱兑换最少枚数：dp[x] 表示组成金额 x 的最少枚数，不可达设哨兵；区分完全背包与每张只能用一次。

### 12.7 实操容易丢分的地方

数组越界、空输入、比较器用 a-b 导致溢出、递归无终止、排序修改原数据却未说明、错误复杂度、没考虑重复元素、输出格式不符。金融金额题先确认单位及精度，优先 long 整数最小单位或合适十进制。

不会最优解时先交正确朴素解和清晰边界，再改进。时间复杂度需要说明最坏或平均，不把 HashMap 的平均 O(1) 当作无条件保证。

## 13. 综合面试：动机、稳定性、沟通与责任

### 13.1 为什么选择农业银行研发和西安

回答由三层组成：对金融科技业务的理解；自己能力与可靠性研发的连接；真实城市选择因素。可以强调希望参与有明确业务价值、重视安全和审计的系统建设，两个项目也围绕一致性、恢复和可验证结果展开。

不能只说“稳定、离家近”，也不能假装完全不考虑个人生活。若西安有真实家庭、学习或长期发展因素，可以诚实说明。具体部门业务、培养制度、技术栈需在官网和正式招聘材料核实，本文不替你编造。

### 13.2 STAR 行为回答

Situation 背景；Task 目标；Action 你的具体行动；Result 结果及反思。重点是 Action，明确谁做了什么，避免整段都是“我们”。

真实可用事例：桌面切换账号后旧响应覆盖新页面。背景是模拟用户测试；目标是隔离身份展示；行动是控制响应时序复现、捕获身份／会话校验、补回归；结果是修复前失败、修复后通过。反思是后端鉴权正确不代表前端异步展示天然正确。

可准备六张素材卡：解决困难、合作分歧、犯错与纠正、时间紧张、快速学习、需求变化。没有实习经历也可使用真实课程、研究、项目经历，不能虚构生产事故。

### 13.3 常见问题的答法

“最大的不足？”选真实且可改进的点，说具体影响、已采取行动与反馈；避免“太追求完美”式套话。

“需求不合理怎么办？”澄清目标与约束，提供成本／风险／替代方案，记录决策；不把争论变成态度问题。

“发现自己提交的 bug？”先确认影响、通知相关负责人、止损与回滚／修复，再补测试和复盘；不隐藏、不甩锅，也不未经流程私自操作生产。

“接受加班吗？”表达理解关键节点协作需求，同时重视计划、质量和效率；不要承诺永远无条件，也不要把加班等同于贡献。

“还有其他 offer 吗？”如实说进展和选择考虑，不编造竞争 offer，也不泄漏无关敏感信息。

“如何看待使用 AI？”承认辅助工具的价值，强调自己核验逻辑、理解源码、测试和承担交付责任；对不理解代码不作独立完成的夸大表述，敏感业务数据遵循组织要求。

“研究方向与开发不一致？”说明可迁移的方法，如建模、实验设计、数据分析、验证；再用具体代码能力补证据，不贬低自己的研究。

### 13.4 群面仅作备选

通知未说明是否无领导小组。若出现讨论，先对目标与评价维度形成共识，表达观点并给理由，倾听、推进时间与总结分歧。不要为了抢角色打断别人，也不要只负责计时却没有实质分析。

银行场景讨论可以从客户价值、风险、数据保护、实施成本、可回滚性和运营可行性比较方案。不是把“安全第一”当作拒绝所有创新的结论。

### 13.5 反问

可问岗位初期参与哪些类型的研发任务、如何进行代码评审与质量培养、团队如何帮助新人理解银行业务。不问通知已明确的事项，不要求面试官评价录取概率。薪酬等可在合适环节向招聘方确认，避免挤占技术交流核心时间。
